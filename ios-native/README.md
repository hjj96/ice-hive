# Ледяной Улей 2.0 — нативная версия (Swift + Metal)

Нативный порт веб-игры (three.js, папка `game/`) на Swift: мир рисует собственный Metal-рендерер из настоящих
3D-мешей веб-версии, интерфейс (HUD, меню, заставка) — SpriteKit-сцена, которую `SKRenderer` рисует в тот же
Metal-проход. Веб-версия — эталон и спецификация: тот же геймплей, тот же русский интерфейс, тот же визуальный стиль.

## Сборка на Mac

```bash
brew install xcodegen
cd ios-native
echo 'DEVELOPMENT_TEAM = ABCDE12345' > Local.xcconfig   # один раз: id своей команды (файл в .gitignore)
xcodegen generate
open IceHive.xcodeproj
```

Подпись берётся из `Local.xcconfig` (его подключает `Signing.xcconfig`), поэтому `xcodegen generate` её не сбрасывает.
Схемы: **IceHive** (Debug, с проверкой Metal API — для разработки) и **IceHive Release** (Release без проверки
Metal API — для замеров на устройстве и скриншотов магазина). Архив для App Store: схема IceHive → *Any iOS Device* →
Product → Archive.

Проект `IceHive.xcodeproj` генерируется из `project.yml` и в git не хранится — после изменения `project.yml`
или добавления файлов снова выполните `xcodegen generate`.

Аргументы запуска (Edit Scheme → Run → Arguments):

| Аргумент | Что делает |
|---|---|
| `-demo combat` | миссия штурмовиком, отряд неуязвим, автопилот, 600 жуков вокруг — их число держится около 600 |
| `-demo beacon` | миссия, отряд у маяка «Альфа», толпа жуков |
| `-demo title` | титульный экран (за ним — станция в режиме демонстрации) |
| `-demo calm` | начало миссии без жуков (режиссёр выключен): освещение и вид станции; в CI — базовая линия (без нагрузки) |
| `-demo smoke` | то же, что `combat` |
| `-demo probe` | `combat` + составляющие «орды» по одной раз в 4 с (оверлей, баннер, тряска, звуки, вибро, орда) |
| `-demo hold` / `-demo extract` | маяки пропущены, отряд держится на лифте; `extract` — лифт поднимается и застывает на +2 с (пятна и трупы на платформе едут вверх) |
| `-demo levelup` / `-demo pause` / `-demo end` | карты улучшений / меню паузы / отчёт миссии (через 1.5 с) |
| `-demo swarmshot` | момент скриншота App Store `2-swarm` (`harness/scenarios/store-shots.mjs`, кадр b): пулемётчик, 12 с миссии, отряд на переходе (0, −5), несколько шагов, 600 жуков вокруг, огонь вверх-влево 1.6 с, затем время почти остановлено (×0.02); графика «высокая», как у скриншотов магазина — сверка с `store/screenshots/6.3/2-swarm.png` |
| `-seconds N` | через N секунд после окончания загрузки пишет в лог `demo done …` (первые 1.2 с в статистику не входят) |
| `-debugHUD` | отладочная панель (fps, время симуляции и мира, кодирование, GPU, жуки на экране, частицы, вызовы) |
| `-class assault\|pyro\|cryo\|gunner`, `-seed N`, `-mute`, `-orient portrait\|landscape` | класс, сид, без звука, фиксированная ориентация |
| `-bugs N` | `combat` / `beacon`: число жуков (не больше лимита уровня графики) |
| `-mscale N` | масштаб картинки мира (пиксели на точку, по умолчанию 2 — как pixel ratio веб-версии на «высокой»; экран iPhone — 3, интерфейс всегда в родном масштабе экрана) |
| `-glintDots` | каждая искра роя дорисовывается сглаженной точкой (по умолчанию выключено — как в веб-версии) |
| `-storeShot` | без отладочной панели даже в Debug (скриншоты магазина) |
| `-failMetal` | проверка: вести себя так, будто Metal не запустился (сообщение вместо бесконечной заставки) |

Без `-demo` / `-debugHUD` сборка Release не пишет в stdout и не ведёт посекундный журнал (`hb`, `hitch`, `first`) —
только unified log (`os_log`).

## Настройки и рекорды

`UserDefaults` под ключами веб-версии `ledulei.<k>` (значения — JSON-текст, как в `localStorage`): `cls` (класс),
`best` (`{"kills":N,"win":S}` — рекорд убийств и лучшая эвакуация в секундах), `muted`, `vol` (0.2…1), `haptics`,
`quality` (`auto` / `low` / `med` / `high`). Версия 1.x (Capacitor, тот же bundle id) хранила их в Capacitor
Preferences = `UserDefaults.standard`, ключи `CapacitorStorage.ledulei.<k>`: при первом запуске 2.0 копируется каждый
такой ключ, которого ещё нет под `ledulei.<k>` (и те, что 2.0 пока не читает, — например, профиль более поздней 1.x),
так что обновление сохраняет рекорд и настройки (`IceHiveCore/SettingsStore.swift`, тесты `SettingsStoreTests`).
Пауза: звук, громкость (100 → 80 → … → 20 %), графика (авто = средняя; низкая / средняя / высокая — лимит жуков
700 / 1400 / 2500, плотность эффектов, тень от фонаря игрока на «высокой»; на «высокой» на ProMotion — 120 Гц, пока
устройство не греется и не включён режим энергосбережения; иначе 60 Гц, под меню — 30 Гц; при перегреве `.serious` —
эффекты не выше средних, без тени, картинка мира 1.5x, при `.critical` ещё и 30 Гц), вибрация. iOS «Уменьшение движения» снижает тряску и отдачу
камеры до 35 % и удлиняет баннеры.

Управление: левая половина экрана — плавающий стик бега, правая — прицел и огонь, кнопки способности и рывка справа.
С клавиатуры (симулятор): WASD/стрелки — бег, IJKL — прицел и огонь, пробел — рывок, Q/E — способность, Esc — пауза.

## Как строится кадр

**Цикл.** `FrameLoop` владеет единственным `CAMetalLayer` (корневой вид `GameView`) и своим `CADisplayLink`
(30 / 60 / 120 Гц через `preferredFrameRateRange`). Каждый тик:

1. берёт слот кадра и drawable **без ожидания** (на GPU не больше двух кадров, арен загрузки — три). `nextDrawable()`
   ждёт, пока композитор вернёт картинку, — до секунды (CI 26ae6ea: 381 мс на главном потоке при простаивающем GPU),
   поэтому `DrawableSource` спрашивает drawable в фоновой очереди в тот момент, когда у тика есть слот, и ждёт ответа
   не дольше 3 мс (свободный drawable отдаётся за микросекунды). Не успел — тик не рисует, а вызов ждёт дальше в
   очереди, и его drawable достаётся следующему тику. Заранее запрошенный запасной drawable стоил бы кадра конвейера, а
   очередь, стоящая в `nextDrawable()`, пока главный поток делает `present`, задерживала его (CI a108d1d: `drawn` в
   `combat` 58 → 33, подвисания 55–229 мс в `draw`); `addPresentedHandler`, по которому можно было бы считать
   drawable'ы, в SDK симулятора нет. Нет свободного слота (GPU не успевает) или drawable (композитор не вернул) — тик только считает:
   симуляция, ввод, HUD, звук и вибро идут в своём темпе, на экране остаётся прошлая картинка, а время эффектов
   копится (`dtCarry`) и отдаётся следующему нарисованному кадру;
2. `SKRenderer.update` → `GameScene.update`: симуляция ядра, события, камера, `MetalWorld.update` (камера всегда;
   позы отряда, инстансы роя с отсечением по пирамиде, эффекты, свет и загрузка в арену — только когда слот есть;
   под меню мир не пересобирается, пока камера стоит), HUD, звук;
3. один command buffer: проходы ниже, `present` (ниже частоты панели — в целевое время тика display link'а, чтобы
   60 Гц на ProMotion и 30 Гц под меню шли ровно), учёт времени буфера (`GPUTimeline`: коммит → запуск → готово, время GPU).

**Проходы** (`MetalRenderer` — планировщик, порядок как в сцене веб-версии; кто что рисует — модули, см. «Metal-рендер мира»
и шапку `MetalRenderer.swift` с ключами порядка):

| # | Проход | Что | Куда |
|---|---|---|---|
| C0, R0 | предпроходы 100, 150 | места для вычислений (частицы на GPU) и карты занятости — пока пусто | свои цели |
| R1 | предпроход 200 `ShadowAtlas` | тень от фонаря игрока («высокая»): меши отряда + прокси жуков в конусе, только глубина | 1024² `depth32Float` |
| R2 | стадия opaque | пол (снег по маске), пропы уровня, лифт, отряд / турели / аптечки / трупы (батчи), рой (по вызову на тип жука) | MSAA 4x `RG11B10Float` + глубина 4x, обе memoryless на устройстве; вьюпорт динамического разрешения внутри цели, выделенной один раз |
|   | стадия transparent | в том же энкодере (тайловая память): дымка, разметка площадки, свечения, пятна (multiply), спрайты на полу, искры-точки, частицы (alpha, затем add), ленты, погода | тот же; в конце прохода — резолв сэмплов в `sceneHDR` (1x `RG11B10Float`) |
| R3 | стадия distortion | тепловое искажение, ¼ разрешения `RG8` (только «высокая» и только пока кто-то рисует в неё) | `RenderTargets.distortion` |
| R4–R12 | `PostChain.encodeBloom` | блум dual-Kawase: префильтр (13 выборок, среднее Кариса против светлячков, мягкий порог) → уменьшения → «шатровые» увеличения с добавлением; «высокая» — от ½ разрешения, 5 уровней, «средняя» — от ¼, 4 | `bloom[0…4]` |
| — | `encodeComposite` | первый вызов финального прохода: апскейл вьюпорта с лёгкой резкостью, искажение («высокая»), + блум, × экспозиция (сценарная), ACES, sRGB, 32³ LUT грейда, яркость (гамма), виньетка, зерно, дизеринг | drawable (3x) |
| — | HUD | `SKRenderer.render` в тот же энкодер, что и композит; затем один `present` | drawable |

**Контракт вывода.** Материалы считают линейную яркость и отдают её через `encodeColor()` / `encodeMultiply()` из
`Shaders/Common.h`: туман exp² подмешивается в линейном пространстве (цвет тумана — линейная яркость), тонмаппинг,
грейд и sRGB — один раз в композите. Поэтому сложение вспышек и частиц идёт в яркости, и ядро взрыва сходит в
тональную кривую градиентом, а не обрезается в плоский диск. Экспозиция — сценарная, без автоэкспозиции:
`PostChain.exposureEV` = EV настроения (`Resources/Look/exposure.json`, когда появится) + EV кадра (кинематографические
планы) + короткий провал после большого взрыва (`dip`). Грейд — `Resources/Grade/<настроение>.lut` (сырые 32³ RGBA8),
пока их нет — встроенный «gameplay»: нейтрально-холодный, с глубоким чёрным (точка чёрного 4 %), мягкой S-кривой,
холодными тенями и чуть тёплыми светами, насыщенность ниже в глубоких тенях и выше в средних тонах; блум плотный
(порог 0.8, сила 0.3, каждый следующий, более широкий уровень весит 0.6 предыдущего), виньетка и зерно лёгкие. `PostChain.brightness` — гамма для опции «Яркость»
(сама опция в настройках — у владельца меню). Для снимков look-dev: `-brightness G` (0.5–2) и `-exposure EV` (EV кадра,
−4…4).

**Качество и разрешение** (`Frame/RenderQuality.swift`). «Высокая» → High (DRS 1.5–2.0 px/pt, блум ½ × 5, искажение;
бюджет iPhone 12 при 1400 жуках ≤ 10.5 мс GPU обычно / ≤ 11.5 пик), «средняя» → Efficient (1.2–1.6 px/pt, блум ¼ × 4;
≤ 6.5 / 7.0 мс), «низкая» → Efficient с полом 1.2 px/pt. Оценки бюджета прохода WP1 на iPhone 12 (`stress1400`):
MSAA + резолв ≈ 0.6 мс, блум ≈ 0.45 мс, финал ≈ 0.8 мс (≤ 1.9 мс вместе), ±50 % — **ни одна цифра не измерена на
устройстве**; время GPU симулятора (CI) — только сигнализация о патологиях. Цель мира выделяется один раз под размер,
который просит `FrameLoop` (масштаб мира `GameScene`), и растёт только при повороте или большем `-mscale`; динамическое
разрешение двигает вьюпорт (регулятор по сглаженному времени GPU к 11.5 мс при 60 Гц, 6.8 мс при 120 Гц, 7.0 мс у
Efficient). Термолестница с гистерезисом 30 с: nominal — выбранный уровень, 120 Гц разрешены; fair — 60 Гц до конца
миссии и пол DRS + 0.1; serious — Efficient + DRS; critical — Efficient на 1.2 px/pt (30 Гц — только последний шаг;
сейчас его включает `GameScene`). 120 Гц — только ProMotion, «высокая», nominal, без энергосбережения и при сглаженном
GPU ≤ 6.5 мс 2 с; после 3 с DRS на полу — до конца миссии 60 Гц. Предел жуков по классу устройства (отдельно от
уровня графики): A13 и старше 900, A14 1400, A15 / A16 1800, A17 Pro и новее 2500 (`RenderQuality.deviceBugCap`;
применяет ядро — запрос владельцу `Tuning`). `-mscale N` фиксирует масштаб; `-drsSweep` (и демо `probe` в CI) делает
10 шагов DRS между краями диапазона раз в 2 с, чтобы показать, что шаг не стоит подвисания.

**Измерение GPU** (`Frame/GPUCounters.swift`). На устройстве (выборка счётчиков на границах стадий) каждый проход
рендерера несёт отметки времени начала и конца в `MTLCounterSampleBuffer` кадра; раз в секунду строка
`hb gpu frame=… max=… shadow=… world=… bloom=… final≈… | ema=… tier=… scale=… range=… view=… alloc=… allocs=…
thermal=… 120hz=… bugcap=… ev=…` (финальный проход открывает `FrameLoop` — пока он не подключает буфер выборок,
`final≈` — остаток кадра). В симуляторе счётчиков нет: только время command buffer'а целиком.

**Куда расти.** Новые форматы вершин (скиннинг, текстуры вершинной анимации) — новый `VertexLayout` (свой
`MTLVertexDescriptor`) + свои вершинные функции; модуль объявляет `PipelineSpec` (мир — MSAA 4x и HDR автоматически,
`.depthOnly` для теней, `.distortion` для тепловых спрайтов) и регистрирует элементы стадий с ключом порядка. Варианты
по уровню — функциональные константы: `PipelineSpec.world(…, tiered: true)` компилирует конвейер дважды (`<метка>.high`
/ `<метка>.efficient`, константа `FC_TIER_HIGH` = индекс 0), модуль рисует `renderer.tieredPipeline(метка)(renderer.frameTier)`;
в шейдере — `TIER_CONSTANT(kИмяHigh);` из `Common.h` один раз на файл (имя своё в каждом файле) и `if (kИмяHigh) { … }`
(ветка вырезается в каждом варианте). Так сделан композит (`kPostHigh`: искажение только у «высокой»). Каждый такой
конвейер — вторая компиляция под заставкой: только там, где уровни правда различаются. HUD остаётся последним
проходом в родном масштабе.

**Загрузка.** Меши, текстуры и 25 конвейеров (20 мира, 5 поста) готовятся в фоне с момента `loadView` (`MetalPreload`), пока на
экране заставка; мир начинает рисоваться под ней, и заставка уходит, только когда GPU вернул ≥ 20 кадров мира, а все
оверлеи HUD, баннер, тосты, меню паузы, отчёт миссии, карты улучшений и каждый вид взрыва / смерти жука / заморозки /
кислоты отрисованы по разу (первые использования не стоят ничего в игре). Переносимый по строкам текст (`TextWarmup`:
все тосты, описания карт, абзацы экранов) раскладывается и рисуется один раз в фоне с `loadView` — первая такая
раскладка в процессе стоила в CI 1.5–9 с на первом двухстрочном тосте посреди миссии; сами двухстрочные тосты
(подсказки о новых жуках, «Вы ранены…») создаются под заставкой и потом переиспользуются.

**Текст HUD.** `SKLabelNode` рендерит новую текстуру на каждую новую строку, и в симуляторе это ждёт GPU хоста, когда
тот стоит. Поэтому часто меняющиеся числа (убито, время, комбо, броня, уровень, расстояние до цели, отладочная панель)
— `GlyphLabel`: моноширинный JetBrains Mono из атласа глифов, отрисованного один раз (`GlyphAtlas`); новое значение лишь
переставляет спрайты. Чтобы числа стояли ровно там, где их рисовал `SKLabelNode`, `GlyphCalibration` перед первым кадром
один раз рисует вне экрана (через `SKRenderer`, в масштабе экрана) эталонный `SKLabelNode` и `GlyphLabel` с одним и тем
же текстом для каждой используемой конфигурации (шрифт, размер, выравнивание, строк), читает пиксели и сдвигает
`GlyphLabel` на разницу их границ (целые пиксели; в логе — `glyph calibration …`). Атласы рисуются под заставкой.

**Текстуры HUD — только под заставкой.** Медленный `SKRenderer.render` в CI — почти целиком ожидание, а не работа
(`hud 339 (cpu 1)`): первая отрисовка новой текстуры (текст, картинка) в симуляторе ждёт хост. Поэтому под заставкой
рисуются все атласы глифов, все 48 текстур сектора перезарядки каждой кнопки, меню и тосты, а панели счёта и задачи —
одна текстура на высоту, растянутая по однородной середине (`Shapes.stretchedPanel`, девять частей `centerRect`), а не
новая на каждую ширину. Новые текстуры посреди миссии остались только у текста баннера, задачи и подсказки (несколько
раз за миссию; поле `labels=` в строке `hitch`).

**Сбой Metal.** Если Metal не запустился (нет устройства, библиотеки или обязательного конвейера) — вместо бесконечной
заставки сообщение «Не удалось запустить графику (Metal). Перезапустите игру.»

**Жизненный цикл.** В фоне display link на паузе (GPU-работы в фоне нет); при уходе в неактивное состояние игра
ставится на паузу; при нехватке памяти сбрасываются кэши текстур HUD и живые частицы (в лог — память до/после).

## CI

`.github/workflows/native-ios.yml` запускается на push в ветки `native*` (macOS-раннер GitHub): `swift test` для ядра,
сборка Debug под симулятор (с оптимизацией Swift `-O` и только arm64 — так fps ближе к реальному), архив Release
под устройство (`generic/platform=iOS`, без подписи) с проверкой того, что уходит в магазин (`release-check.txt`:
версия 2.0.0, имя, `ITSAppUsesNonExemptEncryption`, arm64, иконка, манифест приватности, `default.metallib`, нет
спрайтовых листов, размер), сборка Release под симулятор; затем на симуляторе (iPhone 17 Pro) по очереди:
`firstlaunch` (первый запуск после установки — кэш шейдеров холодный; меряется отдельно), `combat`, `beacon`,
`swarmshot` (+ `swarmshot-dots`), `swarm` (1400 жуков) и `swarm3x` (мир в 3x), `calm` (базовая линия: без жуков и
событий — остаётся только хост), `title`, `landscape`, `probe`, `hold`, `extract`, `levelup`, `pause`, `end`, затем
`-failMetal` (должно появиться сообщение), Release без аргументов (stdout должен остаться пустым) и `release-combat`.
Приложение меряет кадры `-seconds` секунд после строки `scene ready` и пишет `demo done …`; скриншоты снимаются
только после этого (`simctl io screenshot` идёт 5–30 с и тормозит GPU симулятора). Результаты коммитятся в ветку
`ci-results` в папку `<ветка>/<короткий sha>/` (`status.json`, `build.log`, `release-check.txt`, `core-tests.log`,
`bundle.txt`, `metrics.txt`, `fps.txt`, `loading.txt`, `hitches.txt`, `shots.txt`, `alive.txt`, `app-<демо>.log`,
`<демо>-<с>s.png`, `app.log`).

Два взгляда на кадр, и оба в логе:
- **цикл** (что контролирует приложение: главный поток — симуляция, ввод, HUD, звук): `fps`, `worst` в строках `hb`,
  `avgFps / minFps / worstFrame` в `demo done`, строки `hitch` (тик дольше 50 мс: `upd` — сцена + сборка мира,
  `draw` — всё после неё, в скобках по частям: `drawable` (ожидание drawable, ≤ 3 мс), `world` (проходы 1–3), `hud` (композит +
  `SKRenderer`; `cpu` — время процессора главного потока в нём: много меньше `hud` — поток ждал), `commit` (present + commit); `skip=a/b` — тиков без рисования: нет свободного слота / нет свободного
  drawable, `cb` — самый медленный недавний command buffer: коммит → готово, ожидание запуска, время GPU);
- **GPU и композитор** (что увидел экран): `drawn` (кадров, вернувшихся с GPU за секунду), `gap` (дольше всего на
  экране держалась одна картинка), `cbmax`, `gpumax`, `skip` (без слота), `nodraw` (без drawable), `drw` (самый долгий
  `nextDrawable()` в фоновой очереди; главный поток ждёт из него не больше 3 мс); в `demo done` — `drawnAvg / drawnMin / worstGap`.
  Если `cb` ≫ `gpu`, кадр ждал вне приложения: на раннерах GitHub это остановки GPU хоста симулятора (они есть и в
  `calm` без нагрузки).

`metrics.txt` (`ci/frame_metrics.py`) сводит это в таблицу; шаг «Frame metrics gate» — общий порог плана v2.0 для
каждого пакета: у тёплых демо 60 Гц средний fps цикла ≥ 59.5, минимальный ≥ 58, худший тик ≤ 43 мс и нет тиков
дольше 50 мс после первой секунды. Тик, в котором главный поток приложения сам работал < 10 мс, — остановка хоста
симулятора, а не подвисание: работа = `upd + draw` минус время, которое поток провёл вне CPU внутри `SKRenderer`
(`hud` − его `cpu`) и внутри кодирования мира (строка `metal: slow world encode N ms (thread cpu M ms)` — её пишет
`MetalRenderer` для кодирований дольше 8 мс; обычное — ≈ 0.2 мс); такие тики идут в таблицу как `host-stalls`, не валят
порог худшего тика и подвисаний, а минимальный fps прогона, где были только они, держится на прежних 55. Тик 44–50 мс
(строки `hitch` у него нет) — тоже остановка хоста, если максимумы самого приложения за ту секунду (`hb ms … max`,
самый долгий HUD `sk=`, ожидание drawable `drw=`, кодирование мира > 8 мс) в сумме < 10 мс. `drawn` у `swarm3x` и
`release-combat` ≥ 55, а когда GPU хоста стоит сам (`calm` того же прогона без нагрузки < 57 кадров/с) — не меньше `calm` − 2. У меню (`levelup` / `pause` /
`end`, 30 Гц) — только подвисания; у `firstlaunch` — худший тик ≤ 150 мс и доля рендерера в загрузке ≤ 0.5 с: сколько
сцена ждала фоновую подготовку Metal (`metal world ready in N ms`) за вычетом запуска службы компиляции шейдеров
симулятора (`first request N ms` сверх 0.3 с). Сама загрузка сравнивается с 1.6 с в отчёте и валит job только дальше
медианы тёплых + 2.5 с: на холодном запуске GPU хоста симулятора по нескольку секунд отдаёт ~5 кадров/с, пока заставка
ждёт свои 20 (тот же коммит `535ce21` в двух прогонах загрузился за 1.43 и 2.73 с; кадры GPU в секунду под заставкой
печатаются в строке); `drawn` ≥ 55 — только в `swarm3x` и `release-combat`
(остальная сторона GPU — в отчёт: хост симулятора останавливает GPU сам по себе, см. `calm`); медиана сглаженного
времени GPU кадра (`hb gpu … ema=`) ≤ 1.0 мс — сигнализация о патологиях, не бюджет; одно выделение цели мира на
запуск; прогон DRS (`probe`) — 10 шагов и ни одного тика дольше 34 мс в секунды, где менялся масштаб. Строки `hb ms` — разбивка тика по разделам (мс):
сцена (`sim`, `ev`, `cam`, `world`, `hud`, `au`) и мир (`cam`, `mar`, `bug`, `fx`, `up`). Ядро дополнительно гоняет
`swift test -c release --filter PerformanceTests` (строки `[perf]` в `core-perf.log`, на статус не влияет). Шаг
«Privacy manifest check» проверяет, что каждый API с обязательной причиной, который зовёт код (`systemUptime`,
`UserDefaults`, …), объявлен в `PrivacyInfo.xcprivacy`.

### История: SpriteKit или Metal

До 2.0 мир рисовался SpriteKit-спрайтами, пре-рендеренными из веб-версии (пять листов ≈ 14 МБ, ≈ 111 МБ после
декодирования). На ветке `native-metal` оба рендерера шли в CI на одних демо и сидах (симулятор iPhone 17 Pro,
коммиты 24e98d0 … db58a09): у Metal CPU 17–23 % против 31–38 % в `combat` и 20–22 % против 40–44 % с 1400 жуками,
вызовов 36–40 против 74–88, память 41–51 МБ против ≈ 138 МБ на пике загрузки, загрузка 0.9–1.4 с против 1.5–2.0 с,
и настоящее 3D, как в веб-версии. Остался Metal; SpriteKit-рендер мира, листы и их инструменты удалены (последний
коммит с ними — `db58a09`). Тогдашние провалы кадра в `beacon` (160–300 мс) оказались остановками GPU хоста
симулятора, а не работой приложения: у SpriteKit они были в той же доле (`sk=`), а у Metal главный поток ждал
свободный слот кадра внутри `update()` и замирал целиком — теперь он не ждёт никогда (см. «Как строится кадр»).
