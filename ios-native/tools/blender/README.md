# Конвейер ассетов «Ледяного Улья» (Blender, headless)

Источник истины для 3D-ассетов версии 2.0: **headless Blender** (`pip bpy 5.2.2`, ровно Python 3.13, закреплённый
venv). Модели строятся процедурно из Python и остаются редактируемыми художником (`*.blend` с исходной сценой).
Выход детерминирован и коммитится в `App/Resources/`, поэтому iOS-CI Blender никогда не запускает.

```sh
python3.13 -m venv ios-native/tools/blender/venv
ios-native/tools/blender/venv/bin/pip install -r ios-native/tools/blender/requirements.txt   # ≈1.1 ГБ, один раз
ios-native/tools/blender/build.sh               # всё → App/Resources, assets.md5, гейты (≈1 мин)
ios-native/tools/blender/build.sh --verify      # две чистые сборки должны совпасть побайтно и совпасть с закоммиченным
ios-native/tools/blender/build.sh --renders     # + контрольный рендер с игровой камеры (ночная задача) → previews/
ios-native/tools/blender/build.sh --bake-trims  # перезапечь трим-листы в Cycles → kit/trims_src (≈6 мин), затем сборка
ios-native/tools/blender/build.sh --bake-ao     # перезапечь атлас AO деталей → kit/ao_src (≈1 мин; после правки геометрии)
python3 ios-native/tools/blender/gates.py    # только гейты (numpy, без Blender) — для шага CI
```

ASTC кодирует закреплённый `astcenc 5.2.0` (`tools/textures/astc.sh` скачивает релиз Arm и сверяет SHA-256;
сборки «invariant»: одинаковые блоки на любом SIMD и любом числе потоков — проверено). Детали кита Blender строит
детерминированно (фиксированные seed и число потоков). Запекания Cycles — нет: запекание трим-листов «выделенное →
активное» между чистыми запусками гуляет на нескольких пикселях у кромок болтов и заклёпок (до 0,25 по
шероховатости), а атлас AO деталей, одинаковый между запусками на одной машине, на другом процессоре (хост с AVX-512)
отличался на 92 байта ASTC (среднее 0,5490914 против 0,5490913). Поэтому оба запекания — шаги автора: `--bake-trims`
коммитит 8-битный результат в `kit/trims_src/` (`<лист>_normal.png`: X, Y нормали в R, G; `<лист>_orm.png`: AO,
шероховатость, металл, иней), `--bake-ao` — в `kit/ao_src/kit_ao.png` вместе с отпечатком геометрии, для которой он
запечён (`bake.json`: md5 позиций, uv1 и треугольников деталей и их контекста — `ihk.ao_fingerprint`). Сборка кодирует
уже их (мипы, Токсвиг, astcenc) — побайтно одинаково на любом хосте: две чистые сборки дают одинаковые md5
(`--verify`). Сборка и `gates.py` отказываются от запекания AO, сделанного для другой геометрии: правка детали в
`pieces.py` / `kitgeo.py` → `build.sh --bake-ao` и коммит `kit/ao_src/`.

## Что где

| Путь | Что | Владелец |
| --- | --- | --- |
| `ihv.py` | IHV1 v2: существа и бойцы (LOD0–2, VAT, жёсткие кости, скиннинг, дорожки клипов) | WP6 (формат) |
| `ihk.py` | IHK1: статический кит станции | WP6 |
| `iht.py` | IHT1: ASTC-текстуры (мипы, массивы) + сборка мипов и драйвер astcenc | WP6 |
| `kit/` | кит станции: `kitgeo.py` (примитивы с фасками и правилами UV трим-листов), `pieces.py` (детали), `build_kit.py` (Blender: детали, атлас AO — запекание в `ao_src/` → ASTC, экспорт), `trims.py` (4 трим-листа: high-poly → запекание в `trims_src/` → ASTC) | WP6 |
| `gates.py` | гейты ассетов (md5, бюджеты, отчёты сборок существ) | WP6 |
| `build.sh`, `requirements.txt` | сборка, закреплённые пакеты | WP6 |
| `creatures/` | жуки: `insect.py` (общий план тела: ноги с аналитическим IK, трипод, пластины, поры, сокеты), `runner.py` / `spitter.py` / `brute.py` / `boomer.py` (модель трёх LOD + клипы), `build.py` (Blender: риг, меши, AO, ключи клипов, запекание, IHV1, гейты), `build.sh` | WP3 |
| `checks/game_camera.py` | контрольные рендеры отгруженных `*.ihv` (жёсткий путь): лист моделей, полосы клипов, игровая камера с «щелчком» LOD1 → LOD2 | WP3 |
| `characters/` | бойцы | WP4 |
| `env/` | зонд окружения | WP2 |

`build.sh` вызывает `creatures/build.sh`, `characters/build.sh`, `env/build.sh`, если они есть: каждый получает
каталог выхода (`$OUT/Creatures`, `$OUT/Characters`, `$OUT/Env`) и кладёт отчёт гейтов в `reports/<имя>.json`
(`{"gates": {"rigid_vs_vat_m": …, "foot_drift_m": {клип: м}, "ik_err_m": {клип: м}}}`).

## Форматы (все little-endian, секции с шагом 256 байт: файл целиком — один `MTLBuffer`)

- **IHV1 v2** (`*.ihv`): заголовок 128 байт; до 3 LOD (LOD0 ≤ 3000, LOD1 ≤ 450, LOD2 ≤ 150 треугольников);
  жёсткая вершина 20 байт (альбедо+AO, свечение/шероховатость/кость/флаги, half rest, snorm8 нормаль), VAT
  (RGBA16F позиции и нормали по кадрам), текстура костей (3 тексела на кость на кадр), таблица свечения,
  сокеты по 48 байт (вершина на каждый LOD). **Скиннинг** (флаг 4): вершина 32 байта (half rest, snorm8 нормаль и
  тангент, half2 uv, альбедо+свечение, 4 индекса и 4 веса костей), кости по 64 байта с локальной позой покоя,
  **дорожки клипов** (флаг 8): на кадр на кость half4 кватернион + half4 смещение. Версию 1 (бегун-пруф) читает тот же
  код. Полное описание — в шапке `ihv.py`; `ihv.rigid_row` / `ihv.skin_row` — эталон для шейдеров и CPU-палитры.
- **IHK1** (`Kit/station.ihk`): все детали кита; вершина 32 байта: half4 позиция, snorm8 нормаль и тангент (+знак
  бинормали), half2 uv0 (трим-лист), unorm16 uv1 (атлас AO), sRGB-тон + металличность, эмиссия, слой трим-листа,
  флаги (снег, лёд, полосы опасности, фаска, иней, световая полоса, окраска), сила AO. Индексы u16 внутри детали.
- **IHT1** (`*.iht`): ASTC 4×4…8×8 или RGBA8, 2D или массив слоёв, полная цепочка мипов; таблица уровней
  (смещение, байты, байт в строке блоков). Приложение загружает сам (MetalKit в проекте нет): `KitStore.swift`.

## Кит станции (смесь, выбранная пользователем)

База — «Кристалл»: тёмная сталь с фасками, которые ловят фонарь; голубая световая полоса в пазу юбки обводит **только**
край проходимой палубы; по одному цвету света на элемент (бирюзовые колонны и фонари, янтарные площадка и маяк,
оранжевые вентиляции, красные сигнальные огни). Из «Фонарей во тьме» — глубокая тьма: тёмные альбедо, свет дают фонари
и полосы. Из «Инея» — иней на прутьях решётки и кромках у краёв (маска мира × «восприимчивость» трим-листа, слегка),
сосульки под кромками палуб, **низкие** сугробы вдоль перил, в углах палуб и у ящиков — только внутри перил. Палуба остаётся тёмной (серебряная палуба
«Инея» — нет), но она на ступень светлее балок и бездны: крашеная решётка и плита (`WorldLevel.Col.deck` / `.plate`,
металличность 0,3 / 0,22 × маска трима), чтобы тёмный рой читался на ней в свете фонарей и ламп. Замер CI без HUD
(маска `-deckMask`, тестовая ветка `native-vx-station-look`, прогоны 6182a65 и 9426fb5): медиана палубы ≈ 25 /
21–31 / 36–42 (calm / beacon / swarmshot; дальние мостки освещают только лампы и луна, в beacon и swarmshot палубу
местами закрывает рой, кадры анимированы), полоса мира y 700–1900 — 37 / 34–35 / 39–40 (цель смеси 35–50); ни одного
сугроба за линией перил; медиана сугробов в кадре после истончения контура 29 / 30 / 67 (до него 30 / 11 / 79; в
beacon свет на сугробах зависит от кадра).

- Детали (`kit/pieces.py`, бюджеты 40–200 треугольников, мачта маяка до 1500): ящики трёх размеров (окраска
  задаётся при расстановке), колонна-восьмигранник с бирюзовыми полосами, стойка перил, фонарный столб с плафоном,
  вентиляция, решётчатая мачта маяка (янтарные полосы на ногах, светлая крашеная чаша тарелки с янтарным огнём по
  ободу и красным на облучателе, красные огни по углам — в игровом масштабе освещённая мачта, а не тёмный короб),
  вращающаяся голова маяка (цвет состояния), площадка и ступица лифта, три бахромы сосулек, три сугроба, оголовок
  опоры, огонь площадки, кронштейн труб.
- Трим-листы 1024² (2 м на лист): решётки (плитки 1 м, прутья чередуют направление), панели (болтовая, с врезом,
  рифлёная, с прорезями), «перила» (8 полос: юбка с заклёпками и пазом, стенка балки, грань опоры, поручень, проступь,
  полоса опасности, рифлёный лист, шлифованная сталь), «трубы» (8 полос: труба со швами и фланцем, гофра, жгут
  кабелей, уголок решётки, прорези, рёбра плафона, фланец с болтами, резина). Нормаль — ASTC 5×5 (x в rgb, y в
  альфе), ORM — ASTC 6×6 (AO, шероховатость с поправкой Токсвига в мипах, металл, восприимчивость к инею).
- Длинное (палубы, кромки, юбки, перила, балки, опоры, трубы, лестницы, башни) собирается в приложении по раскладке
  уровня (`WorldLevel.swift`) по тем же правилам UV, что `kitgeo.py`, — поэтому сгенерированная станция v1.1
  получает тот же кит (`WorldLevel.rebuild(level:)` пересобирает её без перекомпиляции конвейеров).
- Иней в кадре — не только детали: сугробы приложение масштабирует при расстановке (`WorldLevel.driftScale`: вдоль
  перил ×1,45 по длине, ×1,6 по ширине, ×1,4 по высоте — 3–4 × 0,9–1,1 × 0,2–0,27 м; в углах палуб и у ящиков — только
  шире и выше), иначе в игровом масштабе они в несколько пикселей; каждый сугроб проверяется по сетке проходимости
  (оба конца, середина, дальний край + 0,12 м — внутри линии перил, ровная палуба). Снежную корку на крышках ящиков, рябь
  ветра на сугробах (слабая и неровная, ≈ 0,55 м, без полос и блёсток; гаснет, где гребень уже 3 пикселей), край сугроба,
  истончающийся к контуру (нижняя половина холмика переходит в тёмную решётку, контур рвёт шум маски инея — не
  жёсткая светлая «таблетка»; `KitMesh.place` даёт вершинам сугроба его собственные uv: вдоль и высота над основанием)
  и голубой отсвет полосы в сосульках даёт `fs_level`. Меняя размеры сугробов в `pieces.py`, сверьте их с
  `driftScale`.

**Цена на устройстве** (бюджет: непрозрачная станция ≤ 1,6 мс High / ≤ 1,0 мс Efficient на iPhone 12; оценка ±50 %,
на устройстве не замерено). Счётчики GPU на Apple снимаются только на границах проходов, а станция рисуется внутри
прохода мира, поэтому её цену даёт разность: `-demo stress1400` дважды, с `-noStation` и без, сравнить
`hb gpu frame=` (запуск с `-noStation` — нижняя граница: без палубы видны дымка бездны и слои тумана за ней). Раз в
секунду строка `hb level draws=… tris=… chunks=видимые/все casters=вызовы/треугольники tier=…` (`off` при
`-noStation`) — сколько станции ушло в кадр.

Правка: геометрия и материалы деталей — в `kit/*.py` (затем `build.sh`), рельеф трим-листов — в `kit/trims.py` (затем `build.sh --bake-trims` и коммит `kit/trims_src/`); или в `work/main/kit/kit_src.blend` (атрибуты
граней `tint`, `metal`, `emis`, `layer`, `flags`, UV-карты `trim` и `ao`) и повторный экспорт
`venv/bin/python kit/build_kit.py OUT --from-blend kit_src.blend` (геометрия и атлас AO берутся из файла).

## Существа роя (WP3)

`creatures/build.sh OUT WORK [тип]` → `OUT/Creatures/<тип>.ihv` (жёсткий IHV1 v2 без VAT: три LOD, текстура костей,
таблица свечения, сокеты) и `reports/creature_<тип>.json` (гейты). Модели строятся процедурно из `insect.py` и файла
типа (Blender: X — бок, Y — вперёд, Z — вверх; в игре × масштаб `BUG_SPECS`): части каждого LOD привязаны жёстко к
одной кости; ноги — три сегмента с аналитическим IK по цели стопы в системе груди, походка — трипод, в стойке стопа
уходит назад ровно на шаг клипа за цикл (`gait_foot`), поэтому фаза по пройденному пути ставит ноги без скольжения
(гейт ≤ 2 см за шаг: сейчас 0,4–1,4 см). Флаги вершины: поры (`gland`), глаза, кромки пластин, точки сокетов, **бит 4 —
мешок** (плевун, бумер, брюхо громилы: просвечивает, его пульсирует таблица свечения). Флаги сокета: бит 0 — блик (пора
рисуется ещё и HDR-точкой, `vs_swarm_glint`), бит 1 — горячая (розово-белая), биты 8–15 — радиус в мм, 16–23 —
яркость × 100; плюс сокеты `mouth`, `core`, `back` (и `sac`, `shield`) для эффектов. Клипы: у всех idle / walk / run /
hit; бегун, плевун, громила — attack и 2–3 смерти; плевун — `spit`, громила — `wind`, `charge`; бумер — `swell`
(смертей нет: он лопается). Смерти держат последний кадр как труп; кости смерти опускаются на палубу «зажимом пола»
(`GROUND_CLAMP`). LOD2 (≤ 150) — тот же скелет: 15 треугольников на ногу, тело из трёх-четырёх эллипсоидов, без пор
(поры дают блики). Правка: часть / пора / клип — в файле типа, затем `build.sh` (≈ 4 с на тип); контроль:
`checks/game_camera.py sheet OUT` (лист), `strips OUT [тип]` (клип × 8 кадров), `game OUT` (игровая камера 57° / 45° /
fov 40° на 3× пикселях iPhone: пачка из всех типов в LOD0 / LOD1 / LOD2 и «щелчок» LOD1 → LOD2 — средняя разница
яркости в прямоугольнике жука, гейт ≤ 6).

## Гейты (шаг CI при любом изменении ассетов)

`gates.py`: md5 каждого отгружаемого файла совпадает с `assets.md5` (бинарники = выход сборки); детали кита в
бюджетах, без вырожденных треугольников, нормали единичные, кит ≤ 3 МБ, закоммиченное запекание AO сделано для
отгруженной геометрии; текстуры читаются, всего ≤ 30 МБ; LOD
существ в бюджетах, жёсткий файл ≤ 0,3 МБ (все ≤ 1,5 МБ), бойцы 8–10 тыс. треугольников, веса = 255; отчёты сборок:
жёсткий путь против VAT ≤ 1 мм, скольжение стопы ≤ 2 см за шаг, ошибка IK = 0; новые ассеты ≤ 40 МБ.
«Две чистые сборки → одинаковый md5» проверяет `build.sh --verify` (нужен Blender: локально и в ночной задаче).

Ночная задача (`build.sh --verify` + `--renders`) рендерит отгруженные файлы с игровой камеры (наклон 57°, рысканье
45°, fov 50, 3× пикселя iPhone) — дефекты, видимые только в игровом масштабе.

Состояние: `build.sh` прогоняет `gates.py` после каждой сборки, `build.sh --verify` и `--renders` запускаются
вручную. Задание CI с `gates.py` на каждый push и ночная задача — правки `.github/workflows/` (их владелец — не WP6):
задание `assets` (ubuntu, Python 3 + numpy, ≈ 1 мин) и `assets-nightly.yml` (venv с bpy, `--verify`, рендер с
игровой камеры) переданы владельцу CI готовым YAML; пока их нет, гейты держит автор ассета: `build.sh` (или
`gates.py`) перед коммитом в `App/Resources/`.
